# From materials to an argument

Use this during new planning, restructuring or a “hard to understand” diagnosis. A button repair does not need a new outline.

## Give the audience enough context

Identify who performs the task, the input, the downstream use and the consequence of the current obstacle. Keep background proportional to understanding. A useful planning sentence is: “In this workflow, this role needs this outcome; this obstacle prevents it; this design changes that relationship.” Do not invent financial loss or efficiency gains to complete the sentence.

| Part | Audience question | Useful material |
|---|---|---|
| Context and problem | Why is this needed here? | Original workflow and concrete failure case |
| Core design | Which relationship changes? | Input/output, mechanism and rationale |
| Mechanism and tradeoff | How does it work; what changes with a setting? | Same case across evidence, cost or scope states |
| Verification and result | How was it tested; what happened? | Test setup, expected and actual output with consistent definitions |
| Value and next step | Which downstream action becomes possible or more reliable? | Observed workflow change; measured benefit where available |

Merge or split by content. Do not promote every tool, field table and historical record into a chapter. Independent projects can share business context without pretending to share a pipeline. Identify team versus individual contributions accurately.

## Scene planning

Reuse an existing outline or content model. For complex work, record each scene's theme, main visual and source, default state, object-bound detail, and transition into the next scene. Separately map important claims to source location, evidence status and allowed language. Screenshot, label and title must refer to the same fact.

Prefer specific titles such as “Exception routing: constrained tasks reach a reviewer” over “Tool introduction.” A short subtitle adds the missing context. This title pattern is optional; follow the user's language and house style. A mechanism-only source supports a mechanism title, not an invented performance result.

If human review is the solution's central design, show it in the main view. Full field definitions and logs can be expanded. Asynchronous viewing must expose the problem, mechanism and supported conclusion by default.

## Fictional example: schedule review

This example explains structure; it is not a claim about a real system's performance.

A scheduler automatically assigns ordinary tasks. Tasks with special time constraints need human review. The supplied materials describe trigger reasons and links to original tasks; there is no measured time saving.

1. **Problem:** show one constrained task and its conflicting time window.
2. **Design:** show inputs, rule evaluation and separate automatic/review outputs.
3. **Mechanism:** selecting that same task highlights its constraint, reason and output together.
4. **Verification:** explain a test's expected route beside the actual result, only if the result exists.
5. **Value:** reviewers can locate exceptions and reasons. Do not claim minutes saved without a measurement.

Carry the same object between scenes while each scene answers a different question.

## Diagnose feedback

| Feedback | Check first | Useful response |
|---|---|---|
| “I do not know what this is about” | Missing business context or object | Introduce the workflow and a concrete failure |
| “Too busy” | Competing themes and equal-weight panels | Identify the main visual; bind details to objects |
| “Too technical” | Tools introduced before the design | Explain the mechanism before implementation choices |
| “Looks like a manual” | Everything is a text panel | Represent comparisons, states and transformations visually |
| “Cool but unclear” | Motion detached from input/output | Define a meaningful change or use a static comparison |

Do not cover a structural problem with repeated summaries.
